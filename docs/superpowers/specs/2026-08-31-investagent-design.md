## 1. 项目定位与目标

InvestAgent 是一个以**学习多智能体系统搭建**为核心目标的项目，投研是承载它的真实场景。

- **核心闭环**：用户输入股票代码 → 数据采集 → 多 Agent 协作分析 → 生成结构化投资简报 → 存入记忆库支持跨会话检索。
- **学习主线**：LangGraph 编排能力（State / Schema / Node / Edge / checkpoint / 多 Agent 委派）。
- **可验证性**：财务指标提取准确率作为可量化的评测抓手。

**明确不是目标的**：做一个生产级、覆盖全 A 股的金融产品；追求组件数量的"简历满"。本项目宁可每一块做深，也不堆砌。

### 2.1 组件清单

| 组件 | 用途 | 备注 |
|------|------|------|
| AKShare | 免费真实 A 股数据源 | 利润表/资产负债表/现金流量表/行情/股票列表 |
| LangGraph StateGraph | 编排核心（学习主线） | 阶段 4 升级为动态委派 |
| 4 个子 Agent | 数据采集/财务分析/同业对比/报告撰写 | 见第 4 节 |
| 虚拟文件系统 VFS | 抽象 /workspace /reports /logs | 原始财报落盘不进上下文 |
| SQLite（SqliteSaver） | checkpoint 断点恢复 | 零运维 |
| Chroma | 长期记忆，历史报告向量化检索 | 复用农业助手经验 |
| Streamlit | 前端 | 极简交互 |
| pytest | 测试 | 三层测试 |

### 2.2 明确不引入的组件（原计划书的过度设计）

- **Supervisor**：阶段 4 数据异常需动态委派时才按需引入，不一开始硬上。
- **Milvus**：5 份报告的量，Chroma 足够，免 Docker 运维。
- **PostgreSQL**：checkpoint 用 SQLite 的 SqliteSaver 即可。
- **Redis**：短期会话状态用内存 + State 即可，无需独立服务。
- **LangSmith**：可选，需要账号 key，非核心。
- **SSE 流式**：Streamlit 是 rerun 模型，不原生支持，不做或只做 `st.empty()` 增量刷新。

## 3. 数据流

```
用户输入 "600519"(贵州茅台)
        │
        ▼
[StateGraph 入口]  State = { code, task_list, raw_files, metrics, peers, report, ... }
        │
        ▼
① 数据采集 Agent   ──调用 AKShare──►  财报+行情 落盘 VFS (/workspace/{code}/)
        │                         返回 文件路径(不是数据本体)
        ▼
② 财务分析 Agent   ──读 VFS 文件──►  计算指标 → 写入 State.metrics
        │                          (营收增速/毛利率/净利率/ROE/负债率...)
        ▼
③ 同业对比 Agent   ──采集+分析同行──►  生成对比表 → State.peers
        │
        ▼
④ 报告撰写 Agent   ──汇总 State──►  Markdown 报告 → 落盘 /reports/ + 向量化入 Chroma
        │
        ▼
     返回报告给 Streamlit 展示
```

**核心原则**：数据只在 Agent 之间传"文件路径 + 摘要指标"，原始财报永不进 LLM 上下文。这既是成本优化，也是 VFS 存在的原因。

## 4. 四个 Agent 的职责边界

每个 Agent 都有明确的输入/输出/依赖，可独立理解与测试。

| Agent | 职责 | 输入 | 输出 | 依赖 |
|-------|------|------|------|------|
| 数据采集 | 调 AKShare 拉 3 表+行情，清洗归一化后落盘 | 股票代码 | 文件路径列表 + 采集状态 | AKShare、VFS |
| 财务分析 | 读财报文件，算关键指标，产出结论性判断 | 文件路径 | 指标 dict + 简要分析文字 | VFS、指标计算库 |
| 同业对比 | 定位同行业公司，拉数据算同类指标，做对比表 | 目标公司 + 行业 | 对比表 + 相对强弱结论 | 数据采集 Agent、VFS |
| 报告撰写 | 汇总前三者输出，生成结构化 Markdown | State 全量摘要 | Markdown 报告路径 | 前三者输出 |

**边界设计要点（面试要讲清"为什么这样拆"）**：
- **数据采集是唯一碰 AKShare 的 Agent**，其他 Agent 只读文件——清洗逻辑集中、测试可 mock。
- **财务分析是纯计算**，指标用确定性函数算，LLM 只负责"解读趋势"——体现"哪些地方不该用 LLM"的判断力。
- **同业对比复用数据采集 Agent 的能力**，体现 Agent 可复用。

## 5. 数据清洗归一化（真正的技术难点）

AKShare 的真实痛点与应对：

1. **字段名不稳定**：不同公司列名可能不同（"营业收入"vs"营业总收入"），历史版本也会变。
   → 建**字段映射表**（别名 → 标准字段名），统一解析。
2. **单位不统一**：元/万元/亿元混用，直接比会差 10000 倍。
   → 建**单位归一化函数**，统一为"元"。
3. **字段缺失 / NaN**：某些公司某些季度缺科目。
   → 明确"该指标无数据"，**绝不静默填 0**（0 会让 ROE 等计算崩掉）。

## 6. 评测方法

**主评测：财务指标提取准确率**（替代原计划书的"与券商研报语义相似度"）。

做法：取 5 只不同行业龙头股（消费、新能源、科技、金融、医药各一只），人工从年报标出标准答案（营收、净利润、ROE 等 N 个指标真实值），系统自动计算后对拍：

```
准确率 = 系统算对的关键指标数 / 总指标数
```

该指标**可自动化、可对拍、经得起追问**。语义相似度仅作为"报告可读性"的软参考，不作为主评测。

## 7. 错误处理

| 场景 | 处理方式 |
|------|---------|
| AKShare 拉取失败/超时 | 重试（LangGraph 边 retry），仍失败标记"数据不可用"进降级报告 |
| 股票代码不存在 | 入口校验 + 友好报错 |
| 财务指标算不出（缺字段） | 标注"无数据"，不硬算、不填 0 |
| 流程中断 | SQLite checkpoint 记录状态，重跑从断点续 |

## 8. 测试策略（三层）

- **L1 单元测试**：清洗归一化函数、指标计算函数（确定性，易测）。
- **L2 流程测试**：LangGraph 状态流转是否正确（mock 数据）。
- **L3 端到端评测**：指标提取准确率对拍（阶段 6）。

## 9. 学习主线：6 阶段 + 里程碑

| 阶段 | 学习主题 | 解决的真实问题 | 可交付结果 |
|------|---------|--------------|-----------|
| 1 | LangGraph 基础（State/Schema/Node/Edge） | 怎么把线性流程编排起来 | 输入代码→出 Markdown 报告（数据先 mock） |
| 2 | 工具调用 + AKShare 封装 + 清洗归一化 | 财报字段不稳定、单位不统一怎么处理 | 真实财报正确落盘 VFS |
| 3 | 断点恢复（SQLite checkpoint） | 流程中断/加数据怎么办 | 中断后能续跑 |
| 4 | 多 Agent 协作（委派/消息/条件路由/重试） | 什么时候委派、Agent 间怎么传数据 | 4 Agent 真分工 + 异常动态补采 |
| 5 | 记忆（会话状态 + Chroma 长期检索） | 怎么跨会话复用历史结论 | 语义检索历史报告 |
| 6 | 评测（指标提取准确率对拍） | 怎么证明分析是对的 | 可量化的准确率分数 |

**里程碑**：

| 里程碑 | 阶段 | 交付物 |
|--------|------|--------|
| M1 | 1-2 | 线性流水线 + 真实数据跑通，出第一份报告 |
| M2 | 3-4 | 断点恢复 + 4 Agent 真分工协作 |
| M3 | 5-6 | 记忆检索 + 可量化评测分数 |
